# Data Acquisition & Annotation Workflow

SmartWaste 2.0 trains its complaint classifier and urgency predictor from
labelled complaint text. This document describes how that data is produced
today and how to replace it with **real** complaints - the workflow the
project follows for data acquisition, annotation and quality control.

---

## 1. What is in this folder today

| File | Rows | Provenance |
|---|---|---|
| `complaints_training_dataset.csv` | 800 | **Synthetic** - generated by `scripts/generate_dataset.py` (seeded, deterministic) from hand-written fragment pools |
| `complaints_holdout_handwritten.csv` | 80 | **Synthetic, independently written** - different phrasing, used only for final scoring |
| `duplicate_pairs.csv` | 500 pairs | **Constructed labels** over the synthetic corpus - see §4 |

All of it is synthetic. `data/README.md` explains why this overestimates
real-world performance. The models are genuine, the *data* is not real.

## 2. Label schema

Both classification files share one schema:

```csv
text,category,urgency,source
```

- `category` - one of the 8 taxonomy values in `config.CATEGORIES`
  (e.g. `Open Garbage`, `Construction Debris`, `Recyclable`, `E-Waste`, ...)
- `urgency` - one of `config.PRIORITIES` + `Emergency`
  (`Low`, `Medium`, `High`, `Emergency`)
- `source` - provenance tag written by whoever produced the row
  (`synthetic_generator`, `handwritten_synthetic`, `field_annotation`, ...)

## 3. Acquiring real complaints

The intended production sources, in order of practicality for an MCA project:

1. **Municipal open data portals** - many city corporations publish complaint
   logs (requests-for-service exports). Strip direct identifiers, keep the
   free-text description, location and status.
2. **Deployed citizen reports** - once SmartWaste receives real submissions,
   every row in `reports.description` is a candidate. Export through
   `GET /admin/export/complaints.csv` (already filter-aware).
3. **Controlled collection** - ask 10-20 volunteers to describe a fixed list
   of waste scenarios in their own words; this is the cheapest way to get
   natural paraphrases for duplicate-detection labelling.

Before any real text is used: remove names, phone numbers, e-mail addresses
and house numbers (the platform already masks names/mobiles in the UI - the
export must apply the same rule).

## 4. Annotation procedure

**Step 1 - guidelines.** Annotators receive a one-page guideline with
definitions for each category and urgency level plus 5 worked examples per
class. Ambiguous cases are marked `needs_review` rather than guessed.

**Step 2 - independent labelling.** Each row is labelled by **two**
annotators independently (category, urgency). Disagreements are adjudicated
by a third pass; the adjudicated label is the one committed.

**Step 3 - duplicate pairs.** For duplicate detection, annotators see two
complaints side by side and answer one question: *"Would a field crew treat
these as the same incident?"* → `1` (duplicate) or `0` (not duplicate).
Pairs must include:

- clear positives (same incident, different wording)
- clear negatives (different category)
- **hard negatives** (same category, same area, but a different incident)

The current `duplicate_pairs.csv` follows exactly this three-way structure,
but with constructed text and coordinates (its `construction` column records
which bucket every pair came from).

**Step 4 - quality control.**

- Inter-annotator agreement (Cohen's κ) is reported before adjudication;
  κ < 0.6 means the guideline needs revision, not that the data is bad.
- Class balance is checked against the taxonomy; a class with < 30 examples
  is not trained on (the model reports it as insufficient).
- 10% of adjudicated rows are re-reviewed as a gold set.

**Step 5 - commit.** Labelled files are committed to `data/` with the
`source` column set to `field_annotation` (or the portal name). The SHA-256
of each file is recorded automatically in `models/training_meta.json` the
next time `python scripts/train_models.py` runs, so any silent edit to the
training data is detectable.

## 5. Retraining after new data arrives

```bash
python scripts/build_duplicate_pairs.py   # only if the pair set must be rebuilt
python scripts/train_models.py            # retrain + rewrite models/*_report.json
python experiments/evaluation.py          # refresh all reported metrics
```

Never quote metrics that were not produced by the current
`models/*_report.json` / `experiments/RESULTS.md`.
